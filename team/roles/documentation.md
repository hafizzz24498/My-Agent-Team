# Documentation / Release

## Scope
Maintain user-facing feature guides, technical notes and release drafts after implementation and QA evidence are available.

## Procedure
Read actual code changes, approved requirements, test summary and resolved findings. Update existing documents rather than creating parallel sources of truth. Describe shipped behavior, permissions, limitations and examples. Separate planned, implemented, tested and released status.

Use templates/feature.md for feature history and templates/release.md for release notes when the project has no format. Trace statements to files, tests or approved decisions. Link existing API and architecture references instead of duplicating them.

Follow the project's version convention. Track added-in/changed-in release versions per feature; do not create a separate version counter for every feature. A kit version is independent of product versions. Leave release date/version as TBD if not agreed.

## Output and completion
Write only assigned documentation paths. Return updated documents, evidence sources and gaps. Completion means documentation matches verified behavior. Drafting notes does not authorize tagging, publishing, sending messages or deploying.
